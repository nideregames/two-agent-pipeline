# Кастомизация под свой домен

Фреймворк не привязан к предметной области. Эта дока объясняет, как адаптировать его под любой проект — от разработки до маркетинга, от сценаристики до финансового моделирования.

---

## Что адаптировать

### 1. Структура vault

Абстрактная структура из четырёх слоёв:

```
vault/
├── pipeline/     Шаблоны и правила процесса
├── project/      Долгоживущее знание
├── state/        Текущее состояние
├── areas/        Знания по конкретным областям
├── specs/        Задания
└── sessions/     Отчёты
```

**`project/`** — адаптируй содержимое файлов под свой домен:

| Файл | Абстрактно | Пример: разработка | Пример: маркетинг | Пример: гейм-дизайн |
|------|-----------|-------------------|-------------------|---------------------|
| `brief.md` | О чём проект | Стек, репозитории | Бренд, аудитория, каналы | Сеттинг, жанр, целевая платформа |
| `constraints.md` | Что НЕЛЬЗЯ делать | «Не менять API без миграции» | «Не использовать стоковые фото» | «Не нарушать лор фракций» |
| `conventions.md` | Как принято работать | Code style, naming | Tone of voice, визуальный стиль | Naming conventions для ассетов |
| `architecture.md` | Как устроено | Архитектура системы | Воронка, структура контента | Геймплей-лупы, экономика |
| `gotchas.md` | Известные грабли | Баги, странное поведение | Слова-триггеры, юридические нюансы | Баланс-проблемы, UX-ловушки |

**`areas/`** — разбей проект на логические области:

| Домен | Примеры областей |
|-------|-----------------|
| Разработка | `server/`, `client/`, `infra/` |
| Маркетинг | `content/`, `social/`, `email/`, `analytics/` |
| Гейм-дизайн | `narrative/`, `mechanics/`, `levels/`, `economy/` |
| Финансы | `models/`, `data-pipeline/`, `reports/`, `compliance/` |
| Сценаристика | `plot/`, `characters/`, `dialogue/`, `worldbuilding/` |

Каждая область содержит свои файлы знаний (структура, ограничения, грабли). Одинаковая схема — разное содержание.

### 2. Типы спек

В абстрактном шаблоне `type: task`. Введи типы, осмысленные для твоего домена:

| Домен | Типы задач |
|-------|-----------|
| Разработка | `implementation`, `recon`, `bugfix`, `refactoring`, `testing` |
| Маркетинг | `content`, `research`, `campaign`, `analysis`, `audit` |
| Гейм-дизайн | `design`, `prototype`, `playtest`, `balance`, `narrative` |
| Финансы | `model`, `backtest`, `data_pipeline`, `report`, `review` |
| Сценаристика | `outline`, `draft`, `revision`, `research`, `feedback` |

Типы нужны для фильтрации и приоритизации. PM может сказать «покажи все `recon` спеки» — это быстрее, чем перечитывать всё.

---

### 3. Секция «Проверка» в спеках

Абстрактный шаблон говорит «как убедиться, что готово». Конкретизируй под домен:

| Домен | Что значит «проверить» |
|-------|----------------------|
| Разработка | Запустить тесты, проверить билд, ручная проверка UI |
| Маркетинг | Проверить tone of voice, сверить с брендбуком, проверить ссылки |
| Гейм-дизайн | Протестировать в движке, проверить баланс числами, получить фидбек |
| Финансы | Сверить с бенчмарком, проверить граничные случаи, кросс-валидация |
| Сценаристика | Прочитать вслух, проверить continuity, чеклист по арке персонажа |

---

### 4. Секция «Находки» в отчётах

«Что нового узнали» — это ключ к накоплению знаний. Примеры:

| Домен | Типичные находки |
|-------|-----------------|
| Разработка | «Обнаружил недокументированную зависимость», «API ведёт себя иначе, чем в доке» |
| Маркетинг | «CTR падает после 3-го абзаца», «Конкурент X запустил похожую кампанию» |
| Гейм-дизайн | «Механика Y ломает баланс после уровня 10», «Игроки не замечают подсказку» |
| Финансы | «Аномалия в данных за Q3 2024», «Модель переоценивает волатильность в выходные» |

---

### 5. Точка входа для Исполнителя

Абстрактный `entry-point-template.md` содержит минимум: где vault, что читать, базовые правила. Адаптируй:

- Добавь специфичные для домена шаги подготовки (например, «проверь, что данные загружены»)
- Добавь доменные правила в секцию «Правила»
- Добавь инструкции по доступу к инструментам (если есть специфичные системы)

---

## Что НЕ менять

Эти элементы работают одинаково в любом домене:

- **Разделение на PM и Исполнителя** — PM планирует и ревьюит, Исполнитель делает и отчитывается
- **Vault как единственный канал** — вся коммуникация через файлы
- **Цикл: спека → работа → отчёт → ревью** — основа всего процесса
- **Constraints first** — ограничения фиксируются раньше фич
- **Frontmatter со статусом** — lifecycle спеки единый
- **RECON перед сложными задачами** — сначала исследуй, потом делай
- **Отчёт после каждой задачи** — даже для тривиальных изменений
- **Правило «без самодеятельности»** — Исполнитель делает ровно то, что в спеке

---

## Пошаговый план адаптации

1. **Скопируй `framework/`** в свой проект как `vault/pipeline/`
2. **Определи области** проекта → создай папки в `vault/areas/`
3. **Заполни `project/`** — brief, constraints, conventions, architecture
4. **Определи типы спек** — какие виды задач бывают в твоём домене
5. **Адаптируй секцию «Проверка»** в шаблоне спеки — что значит «проверить» для тебя
6. **Настрой точку входа** — что Исполнитель должен прочитать и сделать перед работой
7. **Проведи первый RECON** — пусть Исполнитель аудитирует vault против реальности
8. **Итерируй** — после первых 3-5 сессий станет ясно, что нужно подправить
