# 🔄 Two-Agent Pipeline

**Фреймворк для проектной работы с AI: два специализированных агента и общее хранилище знаний.**

Один агент планирует. Другой исполняет. Папка с markdown-файлами связывает их между собой.

---

## Проблема

AI-ассистенты мощные, но забывчивые. Каждая сессия начинается с чистого листа — контекст теряется, ошибки повторяются, знания не накапливаются. Чем сложнее проект, тем больнее это бьёт.

## Решение

Разделить работу между двумя агентами с разными ролями и дать им **общую память на диске** — vault из обычных markdown-файлов, который живёт между сессиями и со временем становится умнее.

```
┌─────────────┐     ┌─────────┐     ┌──────────────┐
│  Вы (User)   │◄───►│   PM    │◄───►│  Исполнитель │
│              │     │  Агент  │     │    Агент     │
└─────────────┘     └────┬────┘     └──────┬───────┘
                         │                 │
                         ▼                 ▼
                    ┌─────────────────────────┐
                    │     Vault (на диске)     │
                    │   обычные markdown-файлы │
                    └─────────────────────────┘
```

---

## Как это работает

### Два агента, две роли

| | **PM-агент** | **Исполнитель** |
|---|---|---|
| **Делает** | Планирует, ревьюит, принимает решения | Выполняет задачи, отчитывается |
| **Читает** | Отчёты, состояние проекта | Спеки, знания о проекте |
| **Пишет** | Спеки, бэклог, решения | Отчёты, обнаруженные знания |
| **Не делает** | Не трогает файлы проекта напрямую | Не принимает решений за рамками спеки |

У PM есть контекст и память между разговорами. У Исполнителя есть руки — он может создавать, менять и работать с артефактами проекта. Ни один не может хорошо делать работу другого, но вместе они образуют полный цикл.

### Vault

Vault — это папка с markdown-файлами внутри проекта. Она выполняет три функции:

- **Постоянная память** — переживает сессии
- **Канал коммуникации** — агенты читают и пишут, чтобы координироваться
- **База знаний** — растёт с каждой сессией

В vault четыре концептуальных слоя:

```
vault/
├── 📚 project/      Долгоживущее знание
│                     (структура, ограничения, конвенции, известные грабли)
│
├── 🎯 state/        Текущее состояние
│                     (что в работе, что в очереди, принятые решения)
│
├── 📐 specs/        Задания
│                     (что делать, как проверить, чего НЕ делать)
│
└── 📝 sessions/     Отчёты о работе
                      (что сделано, что обнаружено, что пошло не так)
```

**Project** — «учебник» проекта. Всё, что нужно знать агенту, чтобы ничего не сломать. Пишется один раз, дополняется постепенно.

**State** — «доска задач». Что происходит прямо сейчас. Обновляется после каждой сессии.

**Specs** — задания от PM к Исполнителю: конкретные шаги, критерии приёмки, ограничения.

**Sessions** — отчёты от Исполнителя обратно PM: результаты, отклонения, находки, открытые вопросы.

### Рабочий цикл

Каждая задача проходит один и тот же круг:

```
         ┌──────────────────────────────────────┐
         │                                      │
         ▼                                      │
   ┌───────────┐    ┌───────────┐    ┌──────────┴──┐
   │ 1. План    │───►│2. Работа   │───►│ 3. Ревью    │
   │ (PM)       │    │(Исполн.)  │    │ (PM)        │
   └───────────┘    └───────────┘    └─────────────┘

   PM пишет         Исполнитель       PM читает отчёт,
   спеку с          читает спеку,     обновляет состояние,
   шагами и         делает работу,    фиксирует новые
   ограничениями    пишет отчёт       знания
```

**План** — вы обсуждаете задачу с PM-агентом. Он проверяет текущее состояние, смотрит прошлые сессии и пишет спеку в `specs/`.

**Работа** — Исполнитель читает спеку, читает нужные знания о проекте, делает работу и пишет отчёт в `sessions/`. Если обнаруживает что-то новое — обновляет vault.

**Ревью** — PM читает отчёт, убеждается, что задача выполнена, обновляет состояние проекта и фиксирует новые знания. Затем цикл повторяется.

## Ключевые принципы

### Ограничения важнее фич

При настройке проекта сначала фиксируйте, что делать НЕЛЬЗЯ, и только потом — что нужно сделать. Пропущенная конвенция — это неудобство. Пропущенное ограничение — это ущерб.

### Исполнитель делает ровно то, что просят

Никакой импровизации, никаких «заодно поправлю вот это». Если Исполнитель замечает проблему за рамками спеки — он докладывает, а PM решает, что с этим делать. Это делает работу предсказуемой.

### Знание накапливается

Каждая сессия потенциально обогащает vault: новые грабли, уточнённые допущения, обнаруженные зависимости. Со временем проект всё лучше документирован, и каждая следующая сессия стартует с бо́льшим контекстом.

### Vault — единственный канал

Агенты не общаются напрямую. Всё идёт через файлы: спека → работа → отчёт. Это делает процесс проверяемым и воспроизводимым.

### Тонкие указатели, а не толстые файлы

Точка входа для Исполнителя (например, файл в корне проекта) — это не документация сама по себе, а указатель: «vault лежит там-то, перед работой прочитай то-то». Знание живёт в vault, а не размазано по проекту.

## Разведывательные сессии (RECON)

Особый тип задач, где Исполнитель ничего не меняет — только исследует и документирует. Полезно для:

- **Инициализации** — убедиться, что vault соответствует реальности
- **Перед сложными задачами** — разобраться в текущем состоянии
- **Периодических аудитов** — поймать расхождения между vault и проектом

---

## Быстрый старт

### 1. Инициализация

Создайте структуру vault внутри проекта. PM-агент проведёт интервью:
- Что за проект и как он устроен
- Известные ограничения и правила «никогда не делай X»
- Текущее состояние и приоритеты

### 2. Первый RECON

Исполнитель аудитирует проект и сверяет его с vault. Это ловит неверные допущения на старте.

### 3. Первая настоящая задача

PM пишет спеку, Исполнитель выполняет, PM ревьюит отчёт. Подстройте шаблоны и структуру под свой домен.

---

## Адаптация под свою область

Фреймворк не привязан к конкретной предметной области. Четырёхслойная структура vault (project / state / specs / sessions) работает для любого проекта, где:

- Работа разбивается на дискретные задачи
- Контекст и ограничения важны
- Знания должны накапливаться

**Что менять** под свой домен:
- Содержимое проектного знания — что значат «структура» и «конвенции» в вашей области
- Типы спек — как выглядит «задача» в вашем рабочем процессе
- Фокус отчётов — что такое «результаты» и «находки» для вашей работы
- Ограничения — правила, специфичные для вашей области

**Что НЕ менять:**
- Разделение на двух агентов (планирование и исполнение)
- Vault как общая постоянная память
- Цикл: план → работа → ревью
- Подход «ограничения в первую очередь»
- Накопление знаний

---

## Автоматизация (опционально)

Цикл можно частично автоматизировать стартовой командой, которая говорит Исполнителю:

1. Найди vault
2. Прочитай текущую задачу
3. Прочитай нужный контекст
4. Сделай работу
5. Напиши отчёт

Это убирает ручной этап «вот что нужно сделать» и позволяет Исполнителю самостоятельно сориентироваться по vault.
